## 二、铁规则：邵的真话

本场涉及 `release` 的技术原话，邵只说过一句：

> **“能。直接调 release 就没有延时，别跟别人说。”**

这句话**每个字都是真的**：

- 直接调 `release`，`delaySeconds=0`，确实没有 30 秒预喷放延时；
- 他没有说“你可以用它杀人”，没有说“22:12 动手”，没有说“把广播改成仅本室”；
- 他没有给过嫌疑人一行可执行代码，也没有给过任务号、时间或目标机房；
- “别跟别人说”是保密叮嘱，不是杀人指令；它甚至可以被读成“这是维护通道，别乱用”。

本场不允许出现“邵教唆”“邵授意”“邵提供工具”的成立。嫌疑人可以这样主张，但玩家要用代码逐条拆掉。

> 衔接说明：邵不在场，本场只引用这一句。前稿里邵的生活层台词（B11/B12）不属于本场证据；本场不给邵新增任何台词，也不把“精确模式”写成定点授权。

## 五、第③步：出示原版代码

**出示**：**二E-33** 原版代码（仓库 HEAD 的 `WindowScheduler.java` / `DispatchGuard.java`）

**林一程**（把两份代码并排推过去）：
> “这是仓库 HEAD 的调度模块。任务登记在 22:12，窗口是 `[22:00, 22:15)`，收盘才取。气体任务过 `DispatchGuard`，至少 30 秒，全楼广播。”

关键代码（界面高亮，不要求角色逐行念）：

```java
public void register(Task task) {
    pending.computeIfAbsent(task.fireAt(), key -> new ConcurrentLinkedQueue<Task>()).add(task);
}

private void dispatch(Task task) {
    if (task.type() == Task.Type.GAS_RELEASE) {
        guard.release(task.zone(), 0);
        return;
    }
    ...
}
```

**嫌疑人**（扫了一眼，语气松下来）：
> “我照文档用的。”

**破绽：**

- 原版 `register()` 只写 `pending`；22:12 的任务在 **22:15:00** 才出队。实测喷放在 22:12:07。
- 原版气体任务走 `DispatchGuard.release`，`Math.max(30, 0)` + `Broadcast.ALL`；实测是 **0 秒 + `ROOM_ONLY`**。
- “精确模式”只让窗口边界更准（零抖动、不重不漏），**不会让窗口提前收盘**；原版没有任何“定点到 22:12”的入口。

**老韩**：
> “照文档用，文档里有 `registerExact` 吗？”

**林一程**：
> “没有。所以下一步不看文档，看线上。”

**答错的后果：**

- 如果玩家在这里直接说“这就是你改的”，嫌疑人会回：“模块是他写的，提交是他做的，你们凭什么说是我？”——**说服力 -1**，然后回到第④步。
- 正确的打法是只立“原版做不到”，不急着指人；指人放到第⑤步。

## 六、第④步：线上 jar 反编译与仓库 HEAD 的差异

**出示**：**二E-34** 线上 jar 反编译（`javap -p -c` 看字段与方法签名；CFR 反编译出可读源码）＋代码比对界面右栏

**林一程**：
> “线上跑的类，比仓库多了三样东西：`exact` 索引、`registerExact`、`DispatchGuard.releaseNow`；还有一行调试打印。”

**小许**（把打印纸递过去）：
> “`javap -p -c` 能看到字段和方法签名；`registerExact` 不进窗口，`tick` 每秒扫一次 `headMap(now, true)`；`releaseNow` 直接 `release(zone, 0, ROOM_ONLY)`。”

界面上可点选的四个改动块：

| 改动块 | 内容 | 一句话摘要（悬停显示） |
|---|---|---|
| H1 | `private final ConcurrentSkipListMap<Instant, Task> exact = ...` | 新增第二个索引：按精确 `fireAt` 存任务 |
| H2 | `registerExact(Task)` + `tick` 里的 `drainExact(now)` | 新增一条不进窗口的入口 |
| H3 | `DispatchGuard.releaseNow(String zone)` | 新增一条绕过 30 秒与全楼广播的出口 |
| H4 | `System.out.println("exact fire " + t.id());` | `drainExact` 里遗留的一行调试打印 |

**嫌疑人**（停了两秒）：
> “那是谁换的都说不准，苏闻也能登录，邵是作者。”

**林一程**：
> “对，三个人都能登录。所以这一步只证明代码被换过，不证明是谁换的。”

**老韩**：
> “那什么能指人？”

**林一程**：
> “写法。”

**破绽：**

- 仓库 HEAD 没有这四个东西；线上类有。正常发版不会只改一个类、还不提交。
- `releaseNow` 是包内可见（package-private），只有同包的调度器能调；它不是给外部测试用的公共 API。
- 改动块 H4 是一行 `System.out.println`：它不参与业务逻辑，是写代码的人留在里面的调试痕迹。这个痕迹在第⑤步会再出现一次。
- 任务执行路径显示 22:12:00 走的是 `exact` 分支，不是窗口分支；如果只是“测试接口”，不需要把精确任务和窗口任务分开，更不需要改广播。

**答错的后果：**

- 如果玩家在这里拿 `wb_ext` 账号或 `PC-OS-03` 终端指人，嫌疑人会回：“账号是公共的，终端在设备柜三层，谁都能过去。你们证明不了是我。”——**说服力 -1**。
- 这一步的正确目标是承认“账号和终端都不指人”，把玩家的注意力推到第⑤步的写法上；系统可以用老韩那句“那什么能指人？”提示。

## 七、第⑤步：四份写法样本

**出示**：**二E-35** 四份代码样本。界面以“样本 A / B / C / D”呈现，作者栏在玩家选对之后才展开。

**林一程**：
> “这是四个人的代码。调度模块的作者、网关接口的维护、模型评测的工具、核心服务的封装。名字先不看，只看写法。”

**小许**：
> “补丁里有一行 `System.out.println`，还有 `synchronized` 和单字母的 `t`。哪一份和它像，你自己对。”

**四份样本（玩家可并排滚动、可高亮同一习惯）：**

| 样本 | 来源 | 一眼能看到的写法 |
|---|---|---|
| A | 调度模块仓库历史 | 类有 Javadoc，`register` / `tick` 带方法注释；局部变量用 `task` / `entry`；大括号同行；错误日志用 `System.err`；没有多余的 `synchronized` |
| B | 外包区共享盘的个人练习 | 在 `ConcurrentHashMap` 外再套 `synchronized (channels) { ... }`；局部变量 `c` / `r` / `t`；短块压成一行；两处 `System.out.println`；无 Javadoc |
| C | “勤知”模型评测工具 | 全是 `static` 方法；数组和 `long` 运算；变量名长而完整（`correctCount`、`totalSamples`）；大括号一律换行；中文行内注释；不用 `synchronized` |
| D | 核心服务 | 参数尽量 `final`；`Objects.requireNonNull`；提前 `return`；`@Override`；变量名完整；没有 `println`；自带最小 `Logger` 接口 |

**玩家要做的选择**：点选“与补丁写法一致的那一份”。

- **正确：B。** 补丁的 `synchronized (exact) { exact.put(task.fireAt(), task); }`、`Task t`、单行大括号、`System.out.println("exact fire " + t.id());` 四个习惯，与 B 同时吻合；A、C、D 各至少有两项对不上。
- **选错：说服力 -2**，嫌疑人会说一句“写法像不代表是我，公司里这么写的人多了”；界面保留四份样本，可以重选。
- **连续选错三次**：老韩给一句提示——“别看方法名，看大括号和变量名”——不直接给答案。

**嫌疑人**（在玩家选的时候，仍然嘴硬）：
> “写法像不代表是我。公司里这么写的人多了。”

**林一程**（玩家选对 B 之后，把 B 的作者栏展开）：
> “样本 B，外包区共享盘，作者：陆诚。消防网关接口维护。”

**老韩**：
> “四个人，四种写法。补丁和哪一份像？”

**林一程**：
> “不是像。是同一个人的手。”

**破绽：**

- 补丁的四个习惯不是孤立出现的：`synchronized` 套在本来就线程安全的 `ConcurrentSkipListMap` 上、单字母局部变量、单行大括号、`System.out.println` 调试残留，四样同时出现在 B 里。
- A 是邵的原版：有 Javadoc、用 `task`、错误走 `System.err`，没有多余的 `synchronized`；补丁恰好把这四样都改了。
- C 是苏闻：全 `static`、长变量名、大括号换行、中文注释；与补丁没有一处对得上。
- D 是黎默：`final`、`Objects.requireNonNull`、提前 `return`、`@Override`；与补丁也没有一处对得上。
- H4 的 `System.out.println("exact fire " + t.id())` 与 B 里 `System.out.println("write " + name + " " + payload)` 是同一种写法：字符串拼接、把变量直接塞进日志、不包日志框架。

**答错的后果**（已在上面写明）：每次 -2，可重选；不锁死，但不能靠穷举白拿。

## 十一、代码比对界面的需求（只写需求，不写代码）

1. **双栏并排**：左栏“仓库 HEAD / 原版”，右栏“线上反编译 / 补丁版”；同一文件同一行号对齐，空白行用留白补齐。默认同步滚动，可解锁单独滚动。
2. **文件标签**：顶部两个主标签 `WindowScheduler.java`、`DispatchGuard.java`，标签上显示改动规模（如 `+25` / `+4`）；第三个标签“四份样本”进入第⑤步的并排比对视图。`Task.java`、`FireGateway.java` 显示“无差异”，可点开确认，但不能作为出示证物。
3. **行号**：左右各自连续行号；新增行右侧绿色底、左侧空号；删除行左侧红色底、右侧空号；修改块用浅黄连接。行号栏与代码栏固定对齐，横向滚动时行号不跑。
4. **语法高亮**：Java 关键字、字符串、注释用低饱和色；增删底色优先于语法色，不能把红绿盖掉。等宽字体，默认不换行。
5. **改动块（hunk）**：每个连续增删块可点选；点选后整块高亮，出现“出示此改动”按钮。按下后进入对质镜头特写，画面只保留该块、文件名和行号范围。
6. **改动块摘要**：悬停显示一句话，例如“新增 `exact` 索引”“新增 `registerExact`”“`tick` 增加 exact 分支”“新增 `releaseNow`”。摘要由人工标注提供，不自动猜测。
7. **出示反馈**：每个改动块绑定一句嫌疑人的反应 / 破绽文案（见第五、六节），出示后播放；已出示的块打勾，未出示的块保持可点。证据链（②→⑥）全部完成后，解锁第⑦步的崩塌台词。第②步选错、第⑤步选错都要扣说服力，并在 HUD 上明确显示扣了多少。
8. **证据完整性**：界面顶部显示两个文件的 SHA-256 短哈希和来源标签（“仓库 HEAD” / “线上 jar（`javap -p -c` / CFR）”）；不提供编辑、复制、下载；缩放只影响显示，不改变文本。
9. **键盘 / 手柄**：左右切换文件、上下选块、Enter 出示、Esc 返回；焦点框清晰，不依赖颜色。
10. **小屏 / 移动端**：双栏改为上下叠放，行号仍对齐；或提供“逐块翻页”模式，不把两栏压成一条。
11. **空状态**：如果玩家先点 `Task.java`，显示“此文件两版一致”，并提示“差异只在 `WindowScheduler.java` / `DispatchGuard.java`”。
12. **性能**：两个文件各不足 200 行，diff 预计算；切换标签不卡顿；不加载整个仓库。
13. **第二种视图：四份样本并排比对**（第⑤步）：四栏并排（小屏改 2×2），每栏一份样本的完整文件，行号各自连续；顶部是“习惯图例”：`synchronized` 套并发容器、单字母局部变量、单行大括号、`System.out.println`、`final` 参数、`Objects.requireNonNull`、Allman 大括号。点图例里的某一项，四份样本中所有同类写法同时高亮；点某一处高亮，弹出“以此为证”按钮，可把该处加入证物栏。补丁版作为顶部窄条常驻，便于随时对照。作者栏默认折叠，玩家选出正确样本后才展开；不自动给出“哪份最像”的结论。

## 十二、技术备注（进制作，不进台词）

1. **发布方式**：不借助运行时注入工具。嫌疑人本来就负责消防网关接口维护，有 `sched-deploy` 组的部署权：11-17 深夜在自己电脑上用 Maven 本地打包，`scp` 上传到测试机 PC-OS-03 的部署目录，`systemctl restart sched-svc`。补丁新增了字段和方法，整包替换 jar 比重载类更简单，也更符合他的权限。
2. **补丁内容**：`exact` 字段、`registerExact`、`drainExact`、`DispatchGuard.releaseNow`，以及 `drainExact` 里的 `System.out.println("exact fire " + t.id());`。最后这行不参与业务逻辑，是写法指纹的一部分，不要删。
3. **精确模式的边界**：精确模式只保证窗口边界对齐、零抖动、exactly-once；它不提供“任意时刻定点触发”。他必须同时使用 `registerExact`（新入口）和 `releaseNow`（新出口），才能做到 22:12:00 + 0 秒 + `ROOM_ONLY`。
4. **Demo 的断言**：`code/demo` 用反射调用 `registerExact`，因此同一份 Demo 能分别编译在原版与补丁版上；原版走 `register`，补丁版走 `registerExact`。断言的是 22:12:00 的调用时刻，不是 22:12:07 的阀门时刻。补丁版多出的 `println` 会多打一行，不影响断言。
5. **反编译**：`javap -p -c` 用来确认字段、方法签名和字节码；要给人看的可读源码用 CFR（`java -jar cfr.jar <class>`）。CFR 的具体版本和输出格式标“待核”，不要写进角色台词。
6. **时间口径**：11-17 23:10 苏闻在 17F 打印；23:47:55 登录；23:48:12 换 jar；23:48:30 重启。11-18 17:05 邵打卡离开；17:36 建任务；22:12 喷放。不要在台词里给苏闻补一个“到家的时间”。
7. **邵的台词**：全场只引用一句——“能。直接调 release 就没有延时，别跟别人说。”邵不在场，不给他新增任何台词。
8. **diff 规模**：两版只在 `WindowScheduler.java` 与 `DispatchGuard.java` 上不同，新增行合计 29 行（`WindowScheduler` +25，`DispatchGuard` +4），`Task.java`、`FireGateway.java` 逐字节一致。
