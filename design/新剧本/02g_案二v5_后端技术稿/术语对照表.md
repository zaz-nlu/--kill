## 二、调度与定时任务

| 稿中说法 | 真实术语 / 实现 | 游戏里怎么用 | 状态 |
|---|---|---|---|
| 调度模块 / 时间窗 / 收盘 tick | 自研批量调度器：按 15 分钟窗口聚合任务，窗口 `[start, end)` 左闭右开，边界对齐整刻（:00、:15、:30、:45）；收盘 tick 把整个窗口的任务一次取走。它不是 cron，也不是“到点触发”的闹钟。 | 原版 22:12 的任务在 **22:15:00** 才执行；这是邵的原版设计，也是“算法不能定点杀人”的核心。`registerExact` 是陆诚另加的第二个入口，不是原模块的能力。 | 代码即设定 |
| 精确模式 | 本稿自定义术语：窗口边界对齐整刻、jitter=0、exactly-once（不重不漏）。它让“窗口收盘”这一刀切得更准，**不提供任意时刻定点触发**。 | 苏闻信里的“精确模式，文档里没有”指的是这个开关；陆诚把它曲解成“可以精确到 22:12”，实际他必须另加 `registerExact` 和 `releaseNow` 才能做到。 | 本稿自定义；不要和 NTP/PTP 的“精确时钟”混为一谈 |
| 定时任务（Quartz / Spring `@Scheduled`） | Quartz：`JobDetail` + `Trigger`（`CronTrigger` / `SimpleTrigger`），持久化时有 misfire 策略；Spring `@Scheduled`：`fixedRate` / `fixedDelay` / `cron`，进程内调度，重启后不保留错过的触发（除非自己持久化）。 | 如果玩家问“为什么不用 Quartz”：这是设备批量下发模块，窗口聚合是业务需求；Quartz 的 misfire 补偿反而会“补跑”，不符合“窗口收盘一次取走”的语义。陆诚的 `registerExact` 是绕过窗口，不是换 Quartz。 | API 名称准确；具体版本行为待核 |
| misfire | 错过触发后的补偿策略。Quartz 常见取值：`MISFIRE_INSTRUCTION_SMART_POLICY`、`MISFIRE_INSTRUCTION_FIRE_ONCE_NOW`、`MISFIRE_INSTRUCTION_DO_NOTHING`、`MISFIRE_INSTRUCTION_IGNORE_MISFIRE_POLICY`。 | 可用来解释“原版为什么不会在 22:12 补触发”：窗口调度不是 misfire 补偿；错过收盘就等下一个窗口或不补。**不要写成“精确模式会补跑”**。 | 准确 |

## 四、热修、反编译与取证

| 稿中说法 | 真实术语 / 实现 | 游戏里怎么用 | 状态 |
|---|---|---|---|
| 热修补丁 / 线上类与仓库不一致 | 热替换已加载类：Arthas `jad` 反编译，`redefine` 替换方法体，`retransform` 重新转换。受 JVM Instrumentation 限制，**不能新增/删除方法或字段，也不能改方法签名**；热替换不持久化，重启后回到磁盘上的类。新增成员需要类加载器重新加载或重启模块。 | 线上 `WindowScheduler` 多了 `exact` 字段和 `registerExact`，`DispatchGuard` 多了 `releaseNow`——这已经超出 `redefine` 的能力。剧本里的“热修”应写成**模块类加载器热替换**（或发布系统滚动替换 jar），`jad` 只用于反编译取证。详见文末“技术自洽备注”。 | Arthas 命令准确；热修机制需按此修正，待拍板 |
| 类文件 SHA-256 / 构建物比对 | `sha256sum`（Linux）或 `Get-FileHash`（PowerShell）算哈希；`javap -p -c` 反汇编看方法/字段；`jad` 反编译源码；`jar tf` 看包内类。把线上 class 的哈希与 `git show HEAD:...` 构建出的 class 哈希对比。 | 第二步/第三步证据：线上 class 与仓库 HEAD 构建物哈希不一致，且线上类多出成员；说明不是正常发版。 | 命令准确；具体构建工具（Maven/Gradle）待核 |
| git 提交记录 | `git log --format` / `git log -p -- <file>` 看作者、时间、改动；`git blame` 逐行归属；`git status` / `git diff` 看工作区未提交改动。`blame` 只能归属已提交的行，不能证明热修是谁做的；工作区干净也不等于线上没被改过。 | 补丁没有提交记录；邵 17:05 已打卡；17:36 的热修不在任何 commit 里。破案靠“没有提交”+“终端/账号/在场”，不是靠 `blame` 直接指人。 | 准确 |
| Arthas `jad` / `redefine` / `retransform` | `jad com.beta.sched.WindowScheduler` 反编译已加载类；`redefine /path/WindowScheduler.class` 替换方法体；`retransform /path/...` 重新转换。两者都不能新增方法/字段。`redefine` 遇到 schema 变化会失败，报错文案随版本不同。 | 可用于让玩家看到“线上类比仓库多出什么”；但台词**不要**声称 `redefine` 加了 `registerExact`。 | 命令准确；报错文案待核 |

## 六、待核清单（不要写进角色台词）

- MySQL `ALTER DATABASE ... READ ONLY` 的版本/分支支持情况。
- 公司实际启用的是哪种审计插件；是否开了 `general_log`（建议设定为**没开**）。
- 消防主机、协议网关的厂商、型号、寄存器地址、广播分区配置名。
- 30 秒预喷放延时的规范依据（不同规范/地区可能不同）。
- Arthas `redefine` 失败时的具体报错文案。
- 项目的构建工具与产物路径（Maven `target/` / Gradle `build/`）。

## 七、给台词的约束

1. 角色嘴里不要出现未核实的厂商型号、寄存器地址、错误码细节；用“网关日志”“后台任务详情”“类文件哈希”这类可验证的说法。
2. 邵关于 `release` 的技术原话只有一句：“能。直接调 release 就没有延时，别跟别人说。”这句话字面为真；不要让他说出“精确模式可以定点”这种假话。
3. 陆诚可以说“精确模式是邵教的”，但不能说“邵让我 22:12 喷放”。前者是技术事实，后者是栽赃。
4. 陆诚可以说“工具是他递的”，但代码比对要能拆掉：邵递的是窗口调度器，不是定点工具；`registerExact` 和 `releaseNow` 是陆诚加的。

## 技术自洽备注（给程序/编剧，不进台词）

本稿补丁新增了 `exact` 字段、`registerExact` 方法和 `releaseNow` 方法。JVM Instrumentation 的 `redefine` / `retransform` **不能新增成员**，所以“陆诚用 Arthas `redefine` 热修，给类加了方法”这个说法在技术上不成立。

建议采用下面这版设定，既保留代码比对证据，也不违背工具能力：

- 调度模块跑在支持热替换的模块容器里；17:36:10，`WindowScheduler` / `DispatchGuard` 的类加载器重新加载了新 class，任务状态在数据库，重载不丢任务。
- 17:36:22 用 `wb_ext` 在 PC-OS-03 上建 `TASK-1118-1736`；17:36:41 同一任务把 `firelink.broadcast` 改成 `room_only`。
- 11-19 取证时，小许在测试机上用 Arthas `jad` 反编译**线上已加载的类**，与仓库 HEAD 构建物做 SHA-256 对比；`redefine` 只作为“热替换工具的能力边界”出现在技术说明里，不作为补丁手段。
- 如果坚持“Arthas 打的补丁”，则补丁必须改成只改方法体、不新增成员；但那会失去 `registerExact` 这个最直观的比对证据。推荐采用“类加载器热替换”版本。
