> 用途：给搜查阶段与第四幕第⑥步提供一份“可以直接贴进游戏”的发布记录证物。
> 证物编号：**二E-36**（整份）；下文的 A–F 是界面里可展开的子项。
> 原则：**机器日志只回答“发生了什么”，不回答“是谁”。** 这份记录能证明补丁在案发前一晚已经上线，不能证明是谁上传的。指人要靠第⑤步的写法指纹。

## 二、证物 A：部署 jar 的 `META-INF/MANIFEST.MF`

界面呈现：一行标题“部署目录里的 jar 清单”，下方等宽文本块，`Built-By` 一行可点选高亮。

```text
Manifest-Version: 1.0
Archiver-Version: Plexus Archiver
Created-By: Apache Maven 3.6.3
Built-By: admin
Build-Jdk: 1.8.0_202
```

**读法（可做成悬停注释）：**

- `Created-By: Apache Maven 3.6.3`：这份 jar 是 Maven 打出来的，和仓库的构建方式一致；但它不是 CI 自动产出的那一份（见文件时间与哈希）。
- `Built-By: admin`：构建机上的通用账号，**不是人名**。Maven 默认把执行构建的系统用户名写进这一行；公司构建机统一用 `admin`，谁触发构建都长这样。
- `Build-Jdk: 1.8.0_202`：Java 8，与仓库的 `-source 1.8 -target 1.8` 对得上。
- 清单里**没有** `Implementation-Build`、`Git-Commit` 一类能追到提交号的字段；这份 jar 不是从仓库 HEAD 由 CI 自动打出来的。

## 三、证物 B：文件时间

界面呈现：两行 `ls -l --full-time` 输出，部署目录一行、CI 产物一行；两行的时间戳可点选对比。

```text
$ ls -l --full-time /opt/sched/deploy/sched-core-1.4.2.jar
-rw-r--r-- 1 wb_ext sched-deploy 184320 2026-11-17 23:48:12.418 +08:00 sched-core-1.4.2.jar

$ ls -l --full-time /opt/sched/ci/sched-core-1.4.2.jar
-rw-r--r-- 1 ci     ci           183904 2026-10-21 18:12:40.006 +08:00 sched-core-1.4.2.jar
```

**读法：**

- 部署目录里的 jar，修改时间是 **2026-11-17 23:48:12**。
- CI 产物、以及用仓库 HEAD 重新构建出来的 jar，时间都是 **2026-10-21**。
- 两个文件相差 416 字节。补丁新增了 `exact` 字段、`registerExact`、`drainExact`、`releaseNow` 和一行 `System.out.println`，编译后大出几百字节是合理的；但仅凭字节数不能定案，下面看哈希。
- 部署目录的文件属主是 `wb_ext`、属组是 `sched-deploy`。这两个都不是个人身份。

## 四、证物 C：两个 SHA-256 不一致

> 下列哈希为**示意值**，实装时由构建脚本生成并写入证物；此处只保证长度、格式和“两值不同”。

```text
$ sha256sum /opt/sched/deploy/sched-core-1.4.2.jar
9f2c4e18a7b3d6502c1e8f4a6b9d0c3e5f7182a4c6d8e0b2f4a6c8e0d2b4f6a8  /opt/sched/deploy/sched-core-1.4.2.jar

$ sha256sum /opt/sched/ci/sched-core-1.4.2.jar
3d7a9c0e2b5f8a1d4c6e9f0a3b6d8c1e5f7a9b2d4c6e8f0a2b4d6c8e0f2a4b6d  /opt/sched/ci/sched-core-1.4.2.jar
```

**读法：**

- 两个哈希不一致，说明线上跑的 jar **不是** CI 在 2026-10-21 打出来的那一份。
- 结合证物 F：仓库 HEAD 也没有补丁代码，所以“从 HEAD 重新构建”同样对不上线上。
- 哈希只能证明“这份 jar 来路不同”，不能证明“是谁换的”。

## 五、证物 D：`/var/log/auth.log`

界面呈现：一条 sshd 日志，`wb_ext`、`10.20.3.1`、时间三处可点选；下方一行小字解释 NAT 出口。

```text
Nov 17 23:47:55 PC-OS-03 sshd[22417]: Accepted publickey for wb_ext from 10.20.3.1 port 51544 ssh2: RSA SHA256:3Vt9kQm2pX7dR4sL8nA1cF6hJ0wY5uB9eG2iO4kT6mN
```

**读法：**

- `wb_ext` 是共享服务账号，多人共用；`Accepted publickey` 说明用的是账号绑定的公钥，不是某个人的人名密码。
- `10.20.3.1` 是**外包区办公网与远程接入共用的 NAT 出口**。这个地址不绑定个人：同一出口后面可能是办公室的任意一台机器，也可能是远程接入地址池里的一条会话。
- `scp` 与普通 ssh 登录共用同一个 sshd 入口；auth.log 只记连接建立，不记这次会话传了哪个文件。
- 日志里没有个人用户名、没有客户端主机名、没有工位号。
- 23:47:55 这个时间点，只能说明“有人从外包区出口登录了”，不能说明“谁坐在哪台机器前”。

> 证物组合提示（第⑥步用）：这条登录比 jar 的修改时间早 17 秒，比服务重启早 35 秒。顺序是“登录 → 换 jar → 重启”，是一条完整的发布动作，不是误操作。

### 证物 D-2：没有个人命令历史

```text
$ ls -l /home/wb_ext/.bash_history
-rw------- 1 wb_ext wb_ext 0 Nov 17 23:48 /home/wb_ext/.bash_history
```

**读法：** 共享账号 `wb_ext` 的 shell 历史为空（或指向 `/dev/null`）。`scp`、`systemctl` 这类命令没有留下按人区分的记录；不能用“谁的历史里有这条命令”来指人。

### 证物 D-3：发布日志

```text
2026-11-17 23:48:12  sched-deploy  sched-core-1.4.2.jar  replaced
```

**读法：** 发布日志只有一行，写的是“jar 被替换”和时间；没有操作者字段，没有工单号，没有 commit 号。

## 六、证物 E：systemd journal

界面呈现：`journalctl` 的三行输出，`Stopping` / `Started` 两行可点选。

```text
$ journalctl -u sched-svc --since "2026-11-17 23:40" --until "2026-11-17 23:55"
Nov 17 23:48:30 PC-OS-03 systemd[1]: Stopping sched-svc...
Nov 17 23:48:30 PC-OS-03 systemd[1]: Stopped sched-svc.
Nov 17 23:48:31 PC-OS-03 systemd[1]: Started sched-svc.
```

**读法：**

- 23:48:30 停服务，23:48:31 起服务；中间没有计划内维护窗口，也没有发布单。
- systemd 的 journal 只记录“哪个 unit 被停/起”，不记录“谁执行了 `systemctl`”。
- 这次重启发生在 11-17 深夜，距离案发（11-18 22:12）还有 22 个多小时。补丁不是案发当天临时打上去的。

## 七、证物 F：仓库侧

界面呈现：`git log` 与 `git status` 两段输出；最后一次提交的日期可点选高亮。

```text
$ git log -3 --date=iso --format="%h %ad %an %s" -- src/main/java/com/beta/sched/WindowScheduler.java
8c41e7d 2026-10-21 16:42:11 +0800 邵晓阳 sched: align window boundaries in exact mode
b2d05f1 2026-10-20 11:08:53 +0800 邵晓阳 sched: guard gas release with pre-discharge delay
4e9a1c3 2026-10-19 09:31:27 +0800 邵晓阳 sched: batch drain tasks by window
```

```text
$ git log -1 --date=iso --format="%h %ad %an %s" -- src/main/java/com/beta/sched/DispatchGuard.java
b2d05f1 2026-10-20 11:08:53 +0800 邵晓阳 sched: guard gas release with pre-discharge delay
```

```text
$ git status
On branch release/1.4
nothing to commit, working tree clean
```

**读法：**

- `WindowScheduler.java` 的最后一次提交是 **2026-10-21 16:42:11**，作者邵晓阳。此后没有任何提交。
- `DispatchGuard.java` 的最后一次提交是 **2026-10-20**，此后没有提交。
- 工作区干净：没有未提交的本地改动，也没有“先改代码、再补提交”的痕迹。
- 线上 jar 是 11-17 23:48 换的；仓库里没有对应提交。补丁代码**从未进入 git**。

## 十、附：写法指纹对照（作者层，不进台词）

> 这一节给第⑤步的界面标注用，不是证物正文。四份样本的代码分别在 `code/original/` 与 `code/samples/`。

| 写法习惯 | 邵（`original`） | 陆诚（`FireGatewayClient`） | 苏闻（`ModelEvaluator`） | 黎默（`CoreService`） | 补丁（`patched`） |
|---|---|---|---|---|---|
| 在本来就线程安全的并发容器外再套 `synchronized` | 无 | 有：`synchronized (channels) { ... }` | 无 | 无 | 有：`synchronized (exact) { ... }` |
| 局部变量用单字母 | 否，用 `task` / `entry` | 是：`c`、`r`、`t`、`i` | 否，用 `sampleIndex` / `totalSamples` | 否，用 `workerIndex` / `instanceName` | 是：`Task t` |
| `if` / `for` 的大括号体写成一行 | 否 | 是 | 否，大括号一律换行 | 否 | 是：`synchronized (exact) { ...; }` |
| `System.out.println` 调试残留 | 无；只有 `System.err` 错误日志 | 有，两处 | 无 | 无 | 有：`System.out.println("exact fire " + t.id());` |
| Javadoc | 有，类注释与 `register` / `tick` 方法注释 | 无 | 只有类注释 | 只有类注释 | 无新增 Javadoc |
| 大括号风格 | 同行（K&R） | 同行，短块压成一行 | 全部换行（Allman） | 同行（K&R） | 同行，短块压成一行 |

**一句话：** 补丁在四个习惯上与陆诚的样本同时吻合；另外三份样本各自至少有两项对不上。这不是“像”，是同一套手写习惯。
